# RB-POST3D-08B3D1 independent verification foundation

This stage verifies scientific inputs only. Numerical-assumption execution remains
unconditionally disabled at public freeze, pin, replay, dispatch and regional
kernel boundaries. It grants neither Level-3 readiness nor manufacturer trust,
and does not demonstrate physical-yield calibration.

`verify_detailed_context` validates existing input hashes, combined scientific
identity, execution identity and frozen snapshot bytes. Numerical evidence
requires a snapshot, exact equality with the persisted scientific selection,
literal scientific opt-in, and fail_closed in configuration, selection and
execution identity. Existing scientific configuration excludes execution options;
verification restores an empty schema-only execution_options field locally.
No persisted field, public schema or legacy hashing algorithm changes.

The private `_verify_assumption_inputs` resolves every selected numerical module
revision from immutable snapshot bytes, including selections absent from an
illuminated scene. Existing B1 witness binding checks resolve exact module,
topology, parameterization and evidence revisions, asset fingerprints,
classification, declaration/consistency digests and source relationships. IDs
alone, arbitrary metadata, caller booleans and worker state cannot supply this
authority. Missing records or unresolved provenance fail closed.

Fresh B2 acceptance uses the installed verifier's pvlib and production electrical
kernels with use_cache=False. It recomputes fixed-current consistency, current,
voltage and power conservation, bypass transitions, temperature response and
operating domains, and requires exact persisted consistency-record equality.
The existing B2 implementation/policy identity participates in its internal input
fingerprint. No numerical tolerances are relaxed. A producer PASS or producer
cache entry has no authority. Unavailable calculation rejects verification.

Source records authenticate recorded relationships within the supplied package.
The existing contract permits source-record-backed PAN fingerprints when raw
bytes are unavailable; filenames never authorize filesystem reads. This mode
makes no claim of independently possessing original PAN bytes, authenticating
human authorship, or recovering the producer's exact historical software build.
Hashes cannot authenticate an attacker who replaces every unsigned input.

Limitations start with the unchanged engine-wide list. Each unique enabled
numerical module revision contributes its complete validated declaration slice
in revision-ID order. Identical disclosures from different revisions remain
separate slices. Exact semantic equality rejects missing, modified, reordered
or substituted disclosures even after internal identity hashes are recomputed.
Legacy v0.1 limitations retain historical verification semantics.

`verify_attribution_sources` verifies complete detailed contexts before checking
availability or attribution bindings. Numerical contexts then re-pin exact
module payloads from verified snapshot bytes without calling execution-denying
pinning. Source module hashes, parameterization hashes and physical source
identities remain in their existing structures. Historical abbreviated legacy
attribution verification fixtures retain their original resolution behavior.
The internal completed-interval dark shortcut is unchanged; package verification
never treats darkness or raw frozen mappings as numerical scientific authority.

Existing `verify_run_package` and `persist_run_package` already call these
verifiers. Neither artifacts.py nor canonical.py is modified. Recomputed B2
work occurs once per unique selected revision per verification boundary, never
per timestep or module instance. No new acceptance cache is introduced;
bounded immutable B3 witness caches remain structural checks only. Attribution
verification may independently repeat the boundary calculation, with no inherited
producer acceptance state.

The new regression module uses the three-region real B2 fixture and canonical
rehashing. It covers authorization, policies, source/revision and consistency
tampering, fresh kernel calculation and producer-cache isolation, unavailable
kernels, snapshot mismatch, dark provenance, limitations, attribution mismatch,
package-entry semantic rejection and continued execution denial. It also reuses
unchanged repository regressions for legacy package behavior, fallback, dark
attribution and capability non-readiness. Contexts are input-only fixtures with
backend_not_connected and null numerical results; no actual v0.2 run is claimed.

## Assertion repair

The six assertion corrections preserve the existing production rejection paths:

- Scientific opt-in values `'true'` and `1` raise `SnapshotWitnessError` with
  `must be an explicit boolean`. The B3B witness builder wraps strict option
  validation before the B3D1 opt-in check. Missing and false opt-in still raise
  `NumericalAssumptionInputError` with `scientific opt-in`. The test also checks
  that these errors are not `DetailedInputError`, the dispatch classification
  eligible for availability fallback; invalid scientific intent cannot downgrade.
- Both missing-source cases, including the empty-scene case, raise `ValueError`
  with `unpinned SourceRecord ids` identifying `b2-assumption`. Structural replay
  rejects the unresolved topology/source relationship before the deeper B1
  source-binding check. These tests do not claim to exercise that deeper check.
- The rehashed topology-revision change raises `ValueError` with
  `stale topology revision binding`: pinned evidence still references the
  original topology revision.
- The same-ID foreign definition payload raises `ElectricalParameterizationError`
  with `parameterization payload hash mismatch`. The changed definition fails
  its payload-integrity check before the later numerical revision comparison.

These checks reject tampered inputs even after outer context hashes are rebuilt.
No negative test is removed, and no production validation, scientific policy or
execution gate is changed. B3D1 does not activate numerical-assumption Level-2
execution.

## Remaining B3D2 conditions

Controlled activation must integrate the complete authenticated gate into actual
execution, validate serial/worker/attribution execution and demonstrate a small
persisted Level-2 package. It must establish legacy hash and solver regression
evidence before removing the final execution denial. No pilot, annual benchmark,
weather acquisition, dependency or public persistence-field change is included.

B3D2 integration must address:

- Producer/verifier attribution hash alignment: the v0.2 verifier currently
  hashes `_selected_witness_payload` bytes rather than using
  `DetailedModuleInputSnapshot.scientific_input_sha256`. An actual producer
  must emit the matching identity or the verifier must be aligned before activation.
- Final selected-context authority validation at execution and attribution
  boundaries, including worker instance/revision bindings.
- Worker and solver execution activation behind the complete authenticated gate,
  with serial/process and legacy solver regression evidence.
- Independent verification of actual persisted run packages from a small
  Level-2 numerical-assumption execution, rather than input-only fixtures.
- Duplicate physics-verification cost at context and attribution boundaries;
  measure and resolve any optimization without trusting producer acceptance
  state or weakening independent verification.
